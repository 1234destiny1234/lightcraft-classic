# 26.44.1

## Library

- **Plug-ins start installed programs:** a `programs` permission, granted only by ticking it in the Plug-in Manager, lets a plug-in start a program on the computer with files in a folder of its own and read what the program left there when it ends (`program.list`, `program.start`, the `program.end` hook, a row in the activity stack). macOS finds programs by bundle id, Windows by App Paths and `PATH`, Linux by `PATH`. (no PR)
- **Search the Metadata columns and the People view:** every Metadata filter column has a sticky search box that
  narrows its values as you type (case aside, the grid untouched), and the People view's search box narrows the
  person cards by name while the unnamed faces stay. Hiding the columns or the filter bar, or emptying a box, resets
  the search. Fork #218. (no PR)
- **Capture time from file names:** Edit Capture Time reads the date and time from each photo's file name (`IMG_20260921_143000.jpg` and similar), as dialog mode File name and `photo.setCaptureTime {fromFilename, dryRun}` (#619).

## Import

- **Lightroom history from Lightroom Classic 13 and later:** catalog import reads history steps (and snapshots)
  stored compressed, so they come in as History and Versions instead of being skipped with a warning, and are kept
  in the recovery archive. Decoding is capped at 32 MiB per table; an archive too big with the history settings is
  saved without them instead of not at all. Ported from upstream PR 2838.

## Interface

- **Plug-in settings:** plug-ins can declare settings, kept for the whole app and edited on the plug-in's page (a *Settings…* button in the Plug-in Manager; `plugin.settings`, `plugin.setSettings`). Command and export-destination dialogs open with the values they last ran with (`remember: false` opts a field out), and a command with `prepare: true` is asked first how to run on the selection: it offers its own options, runs at once, or explains why there is nothing to do (`plugin.prepare`). Host feature `settings`; new example `sdk/examples/keyword-picker`. (no PR)
- **Edit In asks which file to edit:** Edit in PhotoCraft / Other Editor offers a copy with adjustments, a copy, or the original (the latter two for JPEG, TIFF, PNG, PSD and WebP), with "Don't ask again" kept in Settings ▸ External Editing. Thanks @rampar20. Fork #616. (no PR)
- **Tools get the panel to themselves:** while Crop, Remove, Red Eye or Masking is in use, Develop's right panel shows only that tool's drawer, as Lightroom Classic does; Basic, Tone Curve and the other global panels come back when the tool is put away. Thanks @deunderscorepaul. Fork #618. (no PR)

## Performance

- **Smoother high quality adjustment previews:** the Lanczos display fit of every settled loupe, Before and hover render reads and writes bytes directly (~30 → ~7 ms at 2560 px, same pixels), so a high quality drag gets ~46 instead of ~28 updates a second. With the setting on, the Histogram panel shows each update's own histogram (HDR bins included), so letting go of the slider no longer changes it; after a drag shown in HDR it keeps the live histogram until the released view renders, instead of flashing the one from before the drag. Thanks @Kaan88. (no PR)
- **Display fit on the GPU:** the loupe's Lanczos display fit runs on the device before the readback (`lcc_gpu::try_render_fitted`, within 1 LSB of the CPU's), so a high quality adjustment update renders in ~5 ms instead of ~22 and a drag gets ~58 instead of ~44 updates a second; the histogram is still the whole frame's. Thanks @Kaan88. (no PR)
- **HDR histogram during drags:** an HDR edit's second render for its HDR histogram reuses the view's stage cache (`pipeline::hdr_histogram_cached`, the same histogram): ~15 → ~8.5 ms per update, so a high quality drag of an HDR edit shown in SDR gets ~50 instead of ~31 updates a second. Thanks @Kaan88. (no PR)
- **HDR textures made on the GPU:** an HDR view rendered on the GPU for an HDR display comes back as its `Rgba16Float` texels, made on the device for the window's headroom, instead of float samples the CPU unpacked and encoded (`lcc_gpu::try_render_hdr_texels`): one update of an HDR edit shown in HDR 86 → 76 ms, the slowest interface frame in its drags 13–14 → 9 ms. Thanks @Kaan88. (no PR)
- **The next photo is sharp at once:** the Detail view prepares its neighbours with the loupe's own render job and adopts the result when you step to one: the adjacent photo is ready 237 → 85 ms (median of 14 filmstrip steps). A jump to a photo further away still renders behind a stand-in. Thanks @Kaan88. (no PR)
- **Fewer preview cache writes:** a photo's view renders reach the disk preview cache as a series: in memory at once, and on disk only the last, once it has been quiet for 0.4 s (`PreviewCache::put_deferred_series`). A high quality slider drag wrote ~119 preview files; it now writes ~2. Thanks @Kaan88. (no PR)
- **Releasing a slider when zoomed in:** after an edit at 1:1 or closer, the part on screen renders once more as one full-quality window in the pane's own slot (its stage cache warm from the drag) instead of one render per tile on screen; only the ring of tiles around it is still prepared for a pan. The view is sharp ~70 ms after letting go; with High quality adjustment previews the drag's last update is that window already. Thanks @Kaan88. (no PR)
- **The original prepared after a look:** once a photo larger than the preview level has been shown whole for 1.5 s with nothing else to render, its full-resolution source is decoded in the background (below the neighbours' prefetch), so the first zoom to 1:1 starts from it: median until every tile is in 2.27 → 1.69 s on 8 raws. A 100 MP raw can still be decoding at the zoom, so the gain varies there. Thanks @Kaan88. (no PR)
- **Canon CRW decodes without an allocation per sample:** the decoder built (and dropped) a "too many samples" error
  string for every sample it wrote; the error is now made only when it happens. All 15 decodable corpus CRWs
  2.86 → 1.19 s (S70 352 → 202 ms, EOS 10D 183 → 49 ms), the same samples. Thanks @Kaan88. (no PR)
- **Canon CR3 decodes its streams in parallel:** every tile's planes, and every subband of a C-RAW plane, are separate
  entropy streams and now decode together (they were decoded a tile at a time), and the samples are placed in the
  image a row at a time in parallel. The same samples: 35 corpus CR3s from 26 bodies decode 6.0 → 3.8 s in all;
  multi-tile C-RAW (EOS 90D, M6 Mark II) 264 → 91 ms. Thanks @Kaan88. (no PR)
- **Hot-pixel noise model by median selection:** each brightness bin of the noise model (thousands of samples) took
  its median by sorting the whole bin; it now selects it (`select_nth_unstable_by`, the lower half's maximum for an
  even count), bit for bit the same median. The hot-pixel step: A7 III 35 → 30 ms, GFX100S 197 → 167 ms, 105 MP
  Hasselblad 155 → 132 ms, the same repaired samples. `examples/open_bench` times decoding and the step apart.
  Thanks @Kaan88. (no PR)

## Fixes

- **Plug-in settings kept on macOS and Windows:** a plug-in's settings and remembered dialog values were saved
  but read back as the defaults, because the read refused a settings path that wasn't already canonical
  (`/var` vs `/private/var`, the `\\?\` prefix on Windows). (no PR)
- **Tab skips hidden filmstrip thumbnails:** thumbnails drawn ahead of the filmstrip's scroll, under the side
  panels, no longer take keyboard focus. (no PR)
- **Samsung NX1 / NX500 / NX3000 / NX mini raws are raws again:** the file sniffer counts TIFF compression 32772 or
  32773 as raw data only with a Samsung Make and a CFA pattern in the same directory (IFD0 or a SubIFD), so these
  SRWs route to the raw decoder while an ordinary PackBits TIFF stays a TIFF. Thanks @Kaan88. (no PR)
- **HDR on Wayland at the desktop's brightness:** the window's SDR white was 1.0 of the extended-linear surface,
  which KWin shows at 80 cd/m² as in scRGB, so with HDR on the app was drawn at 80 cd/m² beside a brighter desktop
  (180–280 cd/m² as KDE's SDR brightness is set) and its highlights reached only headroom × 80. It now takes the
  compositor's reference white for the output it reports the headroom of (`wayland_hdr::best_output`,
  `hdr_display::read_compositor_white`) and draws SDR white at `reference / 80`, as Windows does with the user's SDR
  white level; `<PREFIX>_HDR_PAPER_WHITE` still overrides it. Thanks @Kaan88. (no PR)

## Formats

- **HEIC in every build:** the `heif` feature (HEIC/HEIF decoding) is now on by default for the desktop app and the CLI, so builds from source (`cargo run`, `cargo xtask run` / `install`) open iPhone photos like the release packages do, instead of failing with "HEIC/HEIF support isn't included in this build". Build with `--no-default-features` to leave HEVC out. (no PR)

## Features

- **Masks: folding sections, Color Grading, a bin on each row:** a mask's sliders are grouped in sections that fold (Light with the Curve, Color, Color Grading, Effects, Detail); Color Grading works inside a mask (Shadows, Midtones, Highlights and Global hue, saturation and luminance, CPU and GPU); hovering a mask row shows a bin that deletes it. Point Color inside masks is still to come. Thanks @deunderscorepaul. (#642)
